# CORTHEX-MEMORY: functional spec

[한국어](memory.ko.md)

Stage 04 of CORTHEX's own project, for the `corthex-memory` plugin. Status: draft of 2026-10-24. The maintainer checks it together with the user flows of stage 03; after that check the rows are frozen for the release, and a later change to a row needs the maintainer's decision. When this file and its Korean translation differ, this file is the source.

Inputs: the requirements in [docs/02-prd/memory.md](../02-prd/memory.md) (REQ-001 to REQ-065), the user flows in [docs/03-user-flow/memory/](../03-user-flow/memory/README.md) (FL-001 to FL-012) and the glossary in [docs/01-domain/memory.md](../01-domain/memory.md), whose words this file keeps. This stage added eleven words to the glossary (see [New words](#new-words)). Like the flows, this file assumes the recommendations of decisions D1 to D4, and the rows whose status says `open (D2)` or `open (D3)` change with another answer.

## How to read this file

- Each row is one behaviour of the memory plugin. `From` names the requirements and the flows it serves. Every functional Must requirement has at least one row.
- Status: `active`; `open (D2)` or `open (D3)` while the decision named is open; `proposed` when the row needs a requirement that does not exist yet (see [Behaviour no requirement asks for](#behaviour-no-requirement-asks-for)).
- Numbers that come from a requirement, such as 100,000 tokens or 8,000 bytes, are limits. The curation triggers, the retention period, the recall threshold and the 8-character skip are defaults in the memory configuration. The other numbers, such as the deadlines, are fixed in the code; the trial may change them for a later release.
- "The hook" is a hook script of the memory plugin; stage 06 names the hook event of each host that runs it. "In the background" means the detached process of SPEC-013.
- The non-functional requirements are met through the rows that name them and are tested in QA (stage 12). [The whole plugin](#the-whole-plugin) lists them.

## Answers to the points of the user flows

The [user flows](../03-user-flow/memory/README.md#points-for-the-functional-spec) left fourteen points to this stage.

| Point | Answer | Rows |
| --- | --- | --- |
| 1. Curation triggers | Whichever comes first: at the end of a turn, 10 unprocessed turns or an unprocessed turn older than 30 minutes; at the end of a session, any unprocessed turn; at the start of a session, unprocessed turns left from earlier sessions. | SPEC-010 |
| 2. Devices that disappear | A temporary device curates after every turn and, with sync on, syncs after every curation. Without sync, every start summary says that its memory goes with the device. Turns not curated before the device goes are lost, and nothing can count them. | SPEC-011 |
| 3. Two sessions of one project at once | Each session appends to its own raw log file. A curation lock lets one curation run per project; a lock left for 10 minutes is taken over, and a curator that lost its lock applies nothing. | SPEC-002, SPEC-012 |
| 4. A missing key | The start summary says when curation or recall waits for consent or a memory key, naming the key and where to set it. REQ-029 needs a matching change. | SPEC-022 |
| 5. The user correcting the agent | Only an item's own speaker withdraws it. The user's correction becomes a new user item that supersedes the agent's item, and an item of the user's is superseded only by the user's own words. | SPEC-016 |
| 6. A tombstone without the text | A tombstone holds the item's ID and, for each quote, the device, the raw log entry and the position in it: never the text, nor a hash of it. | SPEC-029 |
| 7. Quotes shared by items | Before a forget, the user sees the other items that quote the same raw text and can forget them too. Text that a staying item quotes is kept whole. REQ-054 needs a matching change. | SPEC-035 |
| 8. Retention and stopped curation | Retention wins. The start summary and the memory status warn 7 days before unprocessed turns reach the retention period. | SPEC-009, SPEC-022 |
| 9. Deleting one project's memory | A new behaviour, with a project tombstone, proposed with a new requirement. | SPEC-037 |
| 10. Size | A request holds whole turns up to 100,000 input tokens, counted with the token counting endpoint when it is large. A turn too large for one request goes in parts, and a consolidation goes in groups by kind and then by time. | SPEC-015, SPEC-019 |
| 11. A pinned item superseded or withdrawn | The pin moves to the item that superseded it. A withdrawn or forgotten item loses its pin. The next start summary says so once. | SPEC-034 |
| 12. Hook timings | Each hook records how long it ran, and the memory status shows the median and the 95th percentile of each hook. REQ-053 needs a matching change. | SPEC-008, SPEC-033 |
| 13. Turning sync on | The user gives the address of a Git repository made for memory. The plugin checks that a read without credentials is refused and a read with the device's own credentials works, stores no credential, and checks again every day. | SPEC-026 |
| 14. Quote checks on older items | A quote is checked once, when its item is first saved. Later steps copy it with its provenance and never check it again. | SPEC-020 |

| Field | What it says |
| --- | --- |
| Input | The fixed instructions and one group of current items, with their kinds, texts, quotes and provenance. The last request: the fixed instructions, the current state and the project's item list. |
| Not sent | Raw log entries; keys; other projects; superseded, withdrawn and forgotten items. |
| Output | JSON in a fixed schema: for a group, merges, each naming the items it merges, with the merged text and the quotes copied from them; for the last request, a shorter current state with its citations. |
| Checked by the server | Schema, refusal and output limit as above. Each merge names two or more current items of the group, and each of its quotes equals a quote of one of them, with its provenance (SPEC-019, point 14). Current state lines as in SPEC-017, citing items of the item list. |
| Failure | That group, or for the last request the current state, does not change, and consolidation stays due. Three failed consolidations in a row stop the project (SPEC-018). |
| Human decision | None before it counts. The merged items stay findable as superseded, and the user can forget the merged item. |

### Embed a prompt for recall (SPEC-023)

| Field | What it says |
| --- | --- |
| Input | The redacted prompt, cut to the input limit of the embedding model (8,192 tokens for `text-embedding-3-small`), and the shortened length of the vector that stage 06 fixes. |
| Not sent | Final answers, other turns, items, keys, and the project's name or folder. |
| Output | One vector. |
| Checked by the server | The vector has the length asked for; the plugin scales it to length 1 before scoring. |
| Failure | Later than 800 ms, or an error → nothing is injected, the failure log notes it, and the prompt goes on (REQ-035). The user sees the count in the memory status. |
| Human decision | None for each prompt. In the trial, the maintainer judges what was injected for a sample of prompts, from the injection log (success measures). |

### Embed items for the search index (SPEC-016, SPEC-019, SPEC-027)

| Field | What it says |
| --- | --- |
| Input | The kind, text and quotes of each new or changed current item, all redacted when they were recorded. |
| Not sent | Raw log text that no item quotes; keys; other projects. |
| Output | One vector per item. |
| Checked by the server | Each vector has the length asked for, and is scaled to length 1. |
| Failure | The item is kept without a vector, and is found by words only until a later curation, consolidation or sync embeds it. The failure log notes it. |
| Human decision | None. |

### Embed a search request (SPEC-025)

| Field | What it says |
| --- | --- |
| Input | The user's search request, as the agent words it, once redacted. |
| Not sent | Items, raw log text and keys. |
| Output | One vector. |
| Checked by the server | As for a prompt. |
| Failure | The search goes by words only, and the agent says so. |
| Human decision | The user reads the results, with their provenance. |

## Notes for later stages

### Stage 05: the memory store

- Per project: raw log files, one per session; the curation record, which stays right when two sessions append at once, with the unprocessed turns, the oldest one's time, how far each raw log file is processed and the failures in a row; the items; the current state's lines, each with its own ID; the item list; the pins; the tombstones and project tombstones; the search index, with words and vectors; and the injection log.
- Per device: the memory configuration (consent with its date and text version, enabled projects, left-out folders and kinds, the retention period, the curation triggers, the temporary device, the curator model, the recall threshold and the skip length, the price list and the sync address), the usage log, the failure log, the hook timings, and the store's format version (REQ-063).
- A forget keeps the positions of an entry's other quotes valid (SPEC-035), and a tombstone names quotes by position (SPEC-029).
- IDs are made by the code at random and never reused. They must not look like the trace IDs of the CORTHEX stages, such as `REQ-001`, so that the project hub does not read them.
- Every rewrite goes through a new file and a move, with a backup and a way to restore it (SPEC-007, REQ-064).
