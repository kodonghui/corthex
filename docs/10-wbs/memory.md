## How to read this file

- Each task (TASK) is a slice of the work that its owner can finish and someone else can check on its own. A pull request may finish several tasks that depend on each other, and names them.
- `From`: the behaviours (SPEC) the task builds. Every behaviour has tasks, and every acceptance criterion of the functional spec is named in the `Done when` of a task that tests it: `SPEC-005's acceptance criteria` names them all, and `SPEC-009's first and third` names them by their order in the functional spec. Where a behaviour's acceptance criteria need a later step, that step's tasks test them.
- `Touches`: the interfaces (API) and records (TBL) whose code the task writes, or `none` for shared code and for checks. Every interface and every record is touched by a task.
- `Depends on`: the tasks that must be done first, or `none`. No task depends on a task of a later step, and the dependencies have no cycles.
- `Owner`: `agent`, the AI agent working in the repository, which opens the pull request; or `maintainer`, for what needs the maintainer's judgement, device or accounts.
- `Estimate`: a size, not a date. For the agent's tasks, S is up to about 300 changed lines of code and tests, M up to about 800 and L up to about 2,000; a larger task is split before it starts. For the maintainer's tasks, S takes under 30 minutes of the maintainer's time, M up to two hours, and L is spread over days, as a trial is.
- `Done when`: what someone else checks. Unless it says otherwise, tests pass on Python 3.8 and on the newest Python, on Linux, macOS and Windows (REQ-060, REQ-061). A task that touches an interface is done only when its outcomes have passing tests; [Outcomes](#outcomes) gives each interface's outcomes and the tasks that test them.
- `Status`: `todo`; `in progress`; `done (#N)`, with the pull request that finished it; or `removed (YYYY-MM-DD)`, for a task that a split or a change replaced. `superseded (D3, 2026-10-27)` marks retained C3 design records, which must not be executed before their replacement plan is confirmed. Tasks are never renumbered or deleted.

## C1: recording and the start summary

Release 0.2.0. The hooks record prompts, final answers and session boundaries for each enabled project. The start summary gets memory's part, which holds only notices and the line `Memory holds nothing for this project yet.` until C2 curates. The memory skill turns memory on and off, shows the memory status, sets what is left out and how long raw logs are kept, deletes all memory and repairs the store record. Nothing calls a model or Git. The tasks come in four groups:

1. The memory library, TASK-001 to TASK-008: the base of every file and lock, the store record and the memory configuration, the logs, finding the project, redaction and the raw log.
2. The hooks, TASK-009 to TASK-017, with the memory part of the start summary, its notices, and the memory worker, which in C1 applies retention and cleans up.
3. The memory skill, TASK-018 to TASK-026.
4. The release, TASK-027 to TASK-030 and TASK-057, with the checks in CI, the walks of the flows and the maintainer's trial.

## Choices this stage made

Each can change at the checkpoint.

1. One file for the memory plugin's tasks, `memory.md`, like the files of the other stages, instead of the stage's default name `wbs.md`.
2. The human view is a Notion database with one row per task and a board by status, one of the stage's two defaults, in the project's records. Its truth is this file, unlike the stage's default (`human`) and like every other stage of this project: a task's status changes here first, in the pull request that finishes the task, and the board follows. GitHub Projects, the other default, would be a second place to look besides those records.
3. Two owners, `agent` and `maintainer`, and estimates as sizes rather than days.
4. C1 in small tasks, each testable on its own; C2 and C3 in larger ones, which are split before each step starts.
5. Where the notes of stages 04 to 06 left a starting point, this plan departs from it in five places:
   - C1 already starts the memory worker at each session start, for retention and clean-up (SPEC-009, SPEC-013), as stage 06 planned; curation joins it in C2.
   - C1's `on` makes the project's empty curation record (TBL-009), which stage 05 lists under C2, since a curation record that is missing later counts as lost; C1's retention also lowers its counts.
   - C1's start summary has two notices, memory that cannot be read and memory waiting for consent. The others wait for what they report: curation, keys, pins and sync. The notice that retention will soon delete unprocessed turns waits for C2 as well, since nothing can curate in C1 and every turn stays unprocessed.
   - C1's memory status reads the usage log, which stays empty until C2 calls the models.
   - The tombstone that a forget leaves on its device comes in C2 with `forget`, and its sync in C3; `delete-project` likewise comes without sync in C2 and leaves its project tombstone from C3.
6. Releases: 0.2.0 after C1, 0.3.0 after C2 and 0.4.0 after C3, each tagged after the maintainer's trial of its step.
