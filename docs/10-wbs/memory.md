## How to read this file

- Each task (TASK) is a slice of the work that its owner can finish and someone else can check on its own. A pull request may finish several tasks that depend on each other, and names them.
- `From`: the behaviours (SPEC) the task builds. Every behaviour has tasks, and every acceptance criterion of the functional spec is named in the `Done when` of a task that tests it: `SPEC-005's acceptance criteria` names them all, and `SPEC-009's first and third` names them by their order in the functional spec. Where a behaviour's acceptance criteria need a later step, that step's tasks test them.
- `Touches`: the interfaces (API) and records (TBL) whose code the task writes, or `none` for shared code and for checks. Every interface and every record is touched by a task.
- `Depends on`: the tasks that must be done first, or `none`. No task depends on a task of a later step, and the dependencies have no cycles.
- `Owner`: `agent`, the AI agent working in the repository, which opens the pull request; or `maintainer`, for what needs the maintainer's judgement, device or accounts.
- `Estimate`: a size, not a date. For the agent's tasks, S is up to about 300 changed lines of code and tests, M up to about 800 and L up to about 2,000; a larger task is split before it starts. For the maintainer's tasks, S takes under 30 minutes of the maintainer's time, M up to two hours, and L is spread over days, as a trial is.
- `Done when`: what someone else checks. Unless it says otherwise, tests pass on Python 3.8 and on the newest Python, on Linux, macOS and Windows (REQ-060, REQ-061). A task that touches an interface is done only when its outcomes have passing tests; [Outcomes](#outcomes) gives each interface's outcomes and the tasks that test them. If a Done when item can be checked only through a hook, command or memory status, or only on a system that the pull request cannot run, the task is done when the other items pass; that item passes in the later task named by the case's Task cell or by stage 12's 'Where the cases run'.
- `Status`: `todo`; `in progress`; `done (#N)`, with the pull request that finished it; or `removed (YYYY-MM-DD)`, for a task that a split or a change replaced. `superseded (D3, 2026-10-27)` marks retained C3 design records, which must not be executed before their replacement plan is confirmed. Tasks are never renumbered or deleted.

## C1: recording and the start summary

Release 0.2.0. The hooks record prompts, final answers and session boundaries for each enabled project. The start summary gets memory's part, which holds only notices and the line `Memory holds nothing for this project yet.` until C2 curates. The memory skill turns memory on and off, shows the memory status, sets what is left out and how long raw logs are kept, deletes all memory and repairs the store record. Nothing calls a model or Git. The tasks come in four groups:

1. The memory library, TASK-001 to TASK-008: the base of every file and lock, the store record and the memory configuration, the logs, finding the project, redaction and the raw log.
2. The hooks, TASK-009 to TASK-017, with the memory part and its notices; worker support is TASK-061, retention is TASK-066 and TASK-067, and the detached launcher and real runtime are TASK-068 and TASK-069.
3. The memory skill, TASK-019 to TASK-026, with its schema, validator and command runner in TASK-063, TASK-064 and TASK-065.
4. The release, TASK-027 to TASK-030 and TASK-057, with the checks in CI, the walks and TASK-030's go/no record; TASK-029 is removed history.
