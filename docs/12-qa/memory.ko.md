# CORTHEX-MEMORY: 시험 계획

[English](memory.md)

CORTHEX 자신의 프로젝트에서 `corthex-memory` 플러그인의 12단계입니다. 상태: 2026-10-27 확인했습니다. 남겨 둔 Git 동기화 설계는 D3로 대체됐습니다. C1을 개발 중이며, 아래 결과는 통과로 표시한 케이스만 확인한 것입니다. C3의 Git 케이스는 대체 표시했습니다. 이 단계에서 확인하는 것은 출시 결정, 곧 출시할지 말지이며, 출시 단계마다 한 번씩 옵니다: C1의 관리자 시험 운영(TASK-029) 뒤의 0.2.0, C2의 시험 운영(TASK-050) 뒤의 0.3.0, 관리자의 기기 두 대에서 동기화한(TASK-055) 뒤의 0.4.0입니다. 결정마다 무엇을 읽는지는 [출시 결정](#출시-결정)에 있습니다. 이 번역과 영어 원문이 다르면 영어 원문이 원본입니다.

입력: [docs/03-user-flow/memory/](../03-user-flow/memory/README.ko.md)의 사용자 흐름(FL-001\~FL-012), [docs/04-functional-spec/memory.ko.md](../04-functional-spec/memory.ko.md)의 기능 명세 완료 조건(SPEC-001\~SPEC-039), [docs/05-erd/memory.ko.md](../05-erd/memory.ko.md)의 기억 폴더, [docs/06-api/memory.ko.md](../06-api/memory.ko.md)의 인터페이스와 그 코드, [docs/10-wbs/memory.ko.md](../10-wbs/memory.ko.md)의 작업과 작업마다 시험하는 결과, [요구사항](../02-prd/memory.ko.md)의 비기능 요구사항, 특히 03\~06단계가 이 단계를 위해 남긴 메모이며, [앞 단계의 메모](#앞-단계의-메모)가 그 메모를 케이스와 잇습니다. 기억 플러그인에는 화면이 없으므로 어떤 케이스도 화면 상태(SCR)를 가리키지 않으며, 대화 안에서 기억 스킬이 하는 답이 화면을 대신하고, 화면 상태 종류의 케이스는 해당하지 않습니다. 2026-10-27에 D1·D2·D4와 요구사항 변경 일곱 개를 확인했고, D3는 02단계의 HTTPS 창구와 서버 안으로 정했습니다. 남겨 둔 Git 동기화 상세의 상태는 `superseded (D3, 2026-10-27)`이며 C3 전에 대체 설계가 필요합니다.

> D3 설계 상태: `superseded (D3, 2026-10-27)`. 이곳에 남겨 둔 Git 동기화 제안은 2026-10-27에 확인한 D3 결정으로 대체됐습니다. 구현하거나 실행할 계획이 아닌 과거 자료입니다. HTTPS 창구와 서버 동기화 설계는 C3 전에 따로 작성합니다. 기기의 저장소는 파일과 SQLite 검색 색인을 유지합니다. 이 표시는 여러 단계가 공유하는 행·설정·예시의 동기화 부분에도 적용하며, 그 C1/C2 부분은 확인된 상태입니다.

## 이 파일을 읽는 법

- 시험 케이스(TC) 하나는 기대 결과가 있는 확인 하나입니다. 새 케이스는 다음 빈 번호를 쓰고 해당 출시 단계에 두며, 번호를 바꾸거나 지우지 않습니다: 더는 맞지 않는 케이스는 행을 남기고, 마지막 결과를 `removed (YYYY-MM-DD)`와 그 이유로 둡니다.
- `근거`: 케이스가 확인하는 것. 흐름(FL); 완료 조건은 `SPEC-002#1`처럼 적어 기능 명세에 적힌 차례로 SPEC-002의 첫째를 가리키고, 동작 전체는 `SPEC-002`처럼 적습니다; 인터페이스의 결과는 `API-002#lock-busy`처럼 [10단계의 결과](../10-wbs/memory.ko.md#결과)의 코드로 적습니다; `commands#…`, `model-calls#…`, `failure-log#…`는 모든 명령, 모든 모델 호출, 실패 기록의 훅과 기억 작업 프로세스가 가질 수 있는 코드로, 그 표의 마지막 세 행입니다; 비기능 요구사항(REQ); 케이스가 필드를 확인하는 저장 단위(TBL). 모든 케이스는 흐름, 완료 조건, 동작, 요구사항 가운데 하나를 가리킵니다.
- `작업`: 케이스를 쓰고 통과시키는 PR의 10단계 작업입니다. 여러 작업이 함께 쓰는 케이스에는 그 작업을 모두 적으며, 그 가운데 첫째가 케이스를 씁니다. 모든 완료 조건에는 `끝났다고 볼 때`에서 그것을 가리키는 작업마다 케이스가 있고, 모든 결과에는 그것을 시험하는 작업마다 케이스가 있습니다.
- `실행 방식`: `contract`는 스키마, 고정 문구, 출시 파일의 확인; `api`는 임시 기억 폴더로 훅 스크립트, 기억 작업 프로세스, `memory.py`를 도구나 기억 스킬처럼 돌리는 `tests/`의 테스트; `e2e`는 Linux, macOS, Windows에서 Claude Code와 Codex로 훅을 돌리는 CI의 훅 검사; `agent`는 흐름을 걷는 도구 에이전트([흐름 걷기](#흐름-걷기)); `manual`은 관리자. `real`은 기억이 직접 관리자의 키나 계정으로 실제 모델 API나 실제 Git 호스트를 비용을 들여 부르는 케이스이며, 이런 케이스는 CI에서 돌지 않습니다. 모든 `agent` 케이스가 쓰는 도구 자신의 모델은 세지 않습니다.
- `기대 결과`: 결과와 그것이 기억 폴더에 미치는 영향: 06단계의 코드, 또는 보이거나 내보내는 것, 그리고 바뀐 것이나 아무것도 바뀌지 않았다는 것. 케이스가 따로 말하지 않으면, 모든 훅은 0으로 끝나고 도구의 세션을 그대로 두며, 어떤 코드, 오류 문구, 키도 대화에 닿지 않습니다.
- `마지막 결과`: `실행 전`, 또는 어디서 돌았는지와 커밋을 적은 결과, 예를 들면 `CI의 Linux, macOS, Windows에서 통과 (커밋 abc1234)`입니다. 성능 결과는 백분위수와 부하도 적습니다. `superseded (D3, 2026-10-27)`은 과거 C3 케이스의 설계 상태이며, 통과나 막힘 같은 실행 결과가 아닙니다. 시험 서버에 대고 통과했다는 것은 기억이 받은 답을 다룬다는 뜻이지, 공급자가 그 답을 준다는 뜻은 아닙니다.

## 케이스가 도는 곳

사용자의 기억 폴더에서는 돌지 않고, 관리자의 기억 폴더에서는 케이스가 그렇다고 말할 때만 돕니다:

- 케이스가 따로 말하지 않으면, `api` 케이스는 CI의 Linux, macOS, Windows에서 Python 3.8과 가장 새 Python으로 돌고(TASK-028), PR 전에 개발자의 기기에서도 돕니다.
- 테스트마다 `CORTHEX_MEMORY_HOME`이 가리키는 새 기억 폴더와, 프로젝트 목록이 따로 있는 임시 홈 폴더를 받으므로, 어떤 케이스도 실제 기억 폴더, 프로젝트 목록, 도구 설정을 읽거나 바꾸지 않습니다.
- 모델 호출은 `CORTHEX_MEMORY_ANTHROPIC_BASE_URL`과 `CORTHEX_MEMORY_OPENAI_BASE_URL`이 가리키는 `127.0.0.1`의 시험 서버로 가며, 시험 서버는 녹음해 둔 답을 줍니다. 기억 전용 키는 테스트가 도는 동안 지어내며 저장소에는 하나도 적지 않습니다. Git은 로컬 bare 저장소에 대고 돌거나, 알려진 호스트마다 그처럼 답하는 `git` 대역으로 돕니다.
- `e2e` 케이스는 TASK-028과 TASK-049가 넓히는 `.github/hook-check/`의 훅 검사입니다: Linux, macOS, Windows에서 검사 워크플로가 고정한 판의 Claude Code와 Codex에 플러그인을 설치하고, 가짜 모델 서버, 지어낸 키, 시연용 프로젝트로 돕니다.
- 고정 자료는 06단계가 말한 대로 [memory-examples.json](../06-api/memory-examples.json)의 예와 지어낸 대화입니다. 어떤 케이스도 실제 대화를 읽지 않으며, 예외는 관리자의 기기에서 관리자 자신의 대화를 쓰는 TASK-029, TASK-046\~TASK-048, TASK-050, TASK-055의 시험 운영과 측정입니다.
- 케이스는 계정이 아니라 역할을 적습니다: 사용자, 에이전트(세션 안의 도구 모델), 관리자, 같은 사용자의 다른 기기, 임시 기기.

## 이 단계가 고른 것

확인할 때 저마다 바꿀 수 있습니다.

1. 기억 플러그인의 계획은 다른 단계의 파일처럼 파일 하나 `memory.md`이며, 이 단계의 기본 이름 `test-plan.md`를 쓰지 않습니다. 걷기의 보고는 기본대로 `docs/12-qa/runs/`에 둡니다.
2. 이 단계의 틀에 없는 `작업` 열을 두어, 케이스마다 맡은 작업이 있고 이 계획과 10단계의 `끝났다고 볼 때`가 같은 말을 하게 합니다.
3. 기억 플러그인에는 화면이 없으므로 브라우저 에이전트 대신 Claude Code와 Codex의 도구 에이전트가 걷고, 된 행은 화면의 종단 간 테스트 대신 훅 검사의 재생이 됩니다.
4. `api` 테스트는 `tests/api/` 대신 0.1.0의 테스트 옆인 `tests/`에 두며, `e2e` 테스트는 `.github/hook-check/`의 훅 검사입니다.
5. 기억이 실제 API나 실제 Git 호스트를 부르는 케이스에는 `real`을 달아, 비용이 들고 답이 달라지는 이 케이스가 CI에서 돌지 않게 합니다.
6. 이 프로젝트의 다른 단계처럼 이 파일이 이 단계의 기준입니다: 케이스의 마지막 결과는 그것을 돌린 PR에서 여기 먼저 바꾸고, Notion 사본이 따라갑니다.
