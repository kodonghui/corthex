## How to read this file

- Each test case (TC) is one check with its expected result. New cases take the next unused number, stay in their release step, and are never renumbered or deleted: a case that no longer applies keeps its row, with the last result `removed (YYYY-MM-DD)` and the reason.
- `From`: what the case checks. A flow (FL); an acceptance criterion, as `SPEC-002#1` for the first of SPEC-002 in the functional spec's order, or a behaviour as a whole, as `SPEC-002`; an outcome of an interface, as `API-002#lock-busy`, with the codes of [stage 10's outcomes](../10-wbs/memory.md#outcomes); `commands#…`, `model-calls#…` and `failure-log#…` for the codes that every command, every model call, and the hooks and the memory worker in the failure log can have, the last three rows of that table; a non-functional requirement (REQ); and the records (TBL) whose fields the case checks. Every case names a flow, an acceptance criterion, a behaviour or a requirement.
- `Task`: the task of stage 10 whose pull request writes the case and makes it pass; a case that several tasks share lists them all, and the first of them writes it. Every acceptance criterion has a case for each task whose `Done when` names it, and every outcome has a case for each task that tests it.
- `Runs as`: `contract`, a check of a schema, a fixed text or a release file; `api`, a test in `tests/` that runs the hook script, the memory worker or `memory.py` with a temporary memory store, as a host or the memory skill would; `e2e`, the hook checks in CI, which run the hooks in Claude Code and Codex on Linux, macOS and Windows; `agent`, host agents walking a flow ([Walking the flows](#walking-the-flows)); `manual`, the maintainer. `real` marks a case in which memory itself calls a real model API or a real Git host, with the maintainer's keys or account and at a cost; such cases never run in CI. The host's own model, which every `agent` case uses, does not count.
- `Expected`: the outcome and its effect on the memory store: the code of stage 06, or what is shown or printed, and what changed, or that nothing did. Unless a case says otherwise, every hook exits with 0 and leaves the host session as it was, and no code, error text or key reaches the conversation.
- `Last result`: `not run`, or the result with where it ran and the commit, such as `pass on Linux, macOS and Windows in CI (commit abc1234)`; a performance result also gives its percentile and its load. `superseded (D3, 2026-10-27)` is a design status for historical C3 cases and never a passing or blocked execution result. A pass against a test server shows that memory handles the answer it was given, not that the provider gives it.

## Where the cases run

Never on a user's memory store, and on the maintainer's only where a case says so:

- Unless a case says otherwise, `api` cases run in CI on Python 3.8 and on the newest Python, on Linux, macOS and Windows (TASK-028), and on a developer's device before a pull request.
- Each test gets a new memory store, named by `CORTHEX_MEMORY_HOME`, and a temporary home folder with its own project list, so no case reads or changes a real memory store, project list or host setting.
- Model calls go to test servers on `127.0.0.1`, named by `CORTHEX_MEMORY_ANTHROPIC_BASE_URL` and `CORTHEX_MEMORY_OPENAI_BASE_URL`, which give recorded answers. The memory keys are made up while the test runs, and none is written in the repository. Git runs against local bare repositories, or as a stand-in for `git` that answers as each known host does.
- The `e2e` cases are the hook checks of `.github/hook-check/`, which TASK-028 and TASK-099 extend: they install the plugin in Claude Code and Codex, at the versions that the check workflow pins, on Linux, macOS and Windows, with a mock model server, made-up keys and a demo project.
- The fixtures are the examples of [memory-examples.json](../06-api/memory-examples.json), as stage 06 asks, and made-up conversations. No case reads a real conversation but the maintainer's own, on the maintainer's device: the trials and measurements of TASK-046 to TASK-048, TASK-050 and TASK-055.
- Cases name roles, not accounts: the user, the agent (the host's model in the session), the maintainer, another device of the same user, and a temporary device.

- Keep TASK-066 and TASK-067 helper evidence separate from actual session starts. TASK-069 and TASK-017 check TC-059–TC-065's worker/session-start steps, and TASK-021 checks TC-061's status display of lock skips. Do not promote partial evidence to a whole-case pass before those integrations.
- TC-338 tests only the detached-launch adapter with a fixture child. Real worker maintenance/lifetime remains TASK-069 and actual session-start integration TASK-017; no direct fixture result promotes TC-056, TC-057, TC-331 or TC-332 to a whole-case pass.
