## 변경과 회귀 경계

이전에는 전부 새 기록인 파일도 원문 잠금 아래에서 다시 만들고 fsync·교체하며 진행 정보까지 다시 저장했습니다. 이제 snapshot staging·fsync를 원문 잠금 전에 마칩니다. 진행 수를 낮춰 저장해야 하면 원문을 두 번 검증하는 사이에 잠금을 풀고 내구성 쓰기를 합니다. 뒤 검증에서 거절되면 다시 정리할 수만 있습니다. 같은 진행 값과 바뀌지 않은 원문은 유지하며, 표지 callback은 여전히 원문 잠금을 쥡니다. 지운 파일의 진행 키는 원문 잠금 해제 뒤에 빼므로 그 사이 새 덧붙임과 표지가 남습니다.

늦게 붙은 바이트는 원래의 원자적 suffix 규칙을 지킵니다. 실제 재작성은 원문 잠금 아래에서 suffix를 옮기고 fsync합니다. 이 쓰기까지 잠금 밖으로 옮기고 계속 커진 파일을 미루는 실험은 연속 덧붙임에서 정리가 밀려 채택하지 않았습니다. 유지보수 취득 대기 총 50ms를 많아야 두 원문 취득이 나누며 다 쓰면 기다리지 않고 한 번 시도합니다. 기존 phase 기한과 기록 훅의 자체 50ms 대기는 유지합니다. 외부 잠금·큰 파일 검증·느린 suffix나 백업·OS 지연·파일시스템 실패까지 무손실을 보장하지 않습니다.

독립 소스 리뷰에서 마지막 백업·교체 구간의 staging stamp 재검증 누락도 찾았습니다. 이제 원본 unlink 직전과 replace 재시도마다 검증합니다. 백업 또는 삭제 정리 중 staging을 제자리에서 바꾸는 회귀 두 개는 보완 전 고정 v1에서 모두 실패했습니다.

회귀 검사는 새 기록과 만료 기록의 snapshot·진행 내구성 구간마다 실제 덧붙임 프로세스를 실행합니다. 고아 표지 복구, 두 번째 취득 거절, staging FD·동일성 검사, 원문 삭제와 진행 키 정리 사이의 새 seq=1·표지 보존도 다룹니다. 연속 덧붙임 검사는 시도마다 만료 seed를 넣고 성공 때 원문 inode 교체를 확인하므로 100번 모두 실제 재작성입니다. 500회 시도·120초·기록 프로세스 10ms 간격 한도는 유지하고 완료 응답을 받은 덧붙임은 전부 보존해야 합니다. 의도된 50ms 잠금 건너뛰기는 따로 셉니다.
