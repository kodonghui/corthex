# 실제 호스트 알림·도구·세션 시작과 훅 재신뢰

[English](2026-11-04-memory-native-compat.md)

Claude Code 2.1.310의 기본 설정에서 실제 하위 에이전트가 자기 부모에게 보내는 질문은 `<agent-message`로 시작합니다. 이전 `host-prompts-1` 목록에는 없어 가짜 알림 하나가 사용자 질문으로 저장됐습니다(#99). C1 수정은 이 접두사를 더하고 판을 `host-prompts-2`로 올립니다. 앞 공백을 처리하며, 일반 사용자 질문이 중간에서 태그를 인용하면 그대로 기록합니다. 실제 관찰 형식을 넣은 회귀시험은 Python 3.8·3.15에서 수정 전에 실패하고 수정 뒤 통과했습니다.

아래 갱신된 Windows 관찰은 현재 MEMORY 제품 45개 파일을 모두 묶습니다. 기준 main `855bc6b463a4a5c57c949d1166b58db3915587c2`에서 제품은 `memory_lib/hooks.py` 하나만 바뀝니다. 뒤에 고친 제어기의 로컬 Windows·Linux 관찰은 아래에 기록하며 최종 세 운영체제 CI는 별도로 필요합니다. 이 보고서로 세 운영체제 전체 사례나 TASK-028을 완료로 올리지 않습니다.

실제로 설치한 호스트 실행 파일과 실제 도구·훅을 쓰되 응답은 고정한 로컬 통신 응답입니다. 가짜 동의·키와 버릴 홈/프로젝트/저장소만 사용하며, 실제 모델·원래 계정 프로필·실제 사용자 기억·전역 플러그인 설치는 쓰지 않습니다. Codex 훅 신뢰 우회는 검사한 도구/시작 방식 시험에만 쓰고 업데이트/재신뢰 시험에는 쓰지 않습니다.

시작 방식 제어기는 clear/compact에서 기록을 끈 채 실제 기록을 만든 뒤, 가짜 프로젝트만 켜고 호스트 명령과 한국어 턴을 보냅니다. 시작 원문을 만들어 넣지 않습니다. clear는 먼저 기록을 끈 채 시작한 다른 세션의 본문 없는 끝 한 개를 남길 수 있지만 선택한 세션은 여전히 네 개 순서를 요구합니다. `/new`는 `startup`이므로 clear의 대체 근거가 아닙니다. Claude는 스트리밍 CLI, Unix Codex는 실제 가상 터미널을 쓰고 Windows 터미널 명령은 별도 조작 관찰입니다.

현재 종합 영수증 `task028-native-compat-windows-v4.json`의 SHA256은 `a9fdc6aba0b7aa8b7ebe680043fe53f0c9877afbf36da2b4cb135289b387c5d0`입니다. 제품 해시 45개, 실제 설치 캐시, 판정 영수증 일곱 개와 보존한 실패를 묶습니다. 기준 main이 그대로였던 옛 `task028-native-compat-windows-v1.json`(SHA256 `81bc6e41f7d601960cdea9d9ac979b88e868d9753908db653209bca80bc7529e`)은 과거 근거로 보존합니다.

PR #100의 첫 head `118cdd3bba65d7b1d2a4185398ca70935cd56ed0`은 자동 실행 `41724510609`에서 단위시험 여섯 칸·Node/strict·Windows 실제 호스트 CI를 통과했습니다. Linux와 macOS는 각각 실제 호스트 제어 두 단계가 실패해 `all-checks`가 실패했습니다. Codex 압축 화면은 시작 훅보다 먼저 끝나며 시작 훅은 다음 입력에서 실행됩니다. 수정 제어기는 실제 압축 완료 화면과 그 명령의 완료 신호를 모두 본 뒤 다음 한국어 턴을 보냅니다. 완료 신호를 늦춘 제어 시험은 Python 3.8·3.15에서 먼저 실패한 뒤 수정하여 통과하며, 실제 Unix 재현이라고 보지 않습니다. 신뢰 제어기는 아래 방향키와 Enter를 따로 보내며 실제 저장된 신뢰 해시 한 개/네 개 조건을 유지합니다. CI 전부터 Unix 실행을 고쳤다고 판단하지 않습니다. 아티팩트에서는 생성된 Codex 인수 실행기 사본만 빼고 보고서·터미널 근거는 유지합니다.

현재 제품으로 한 Windows 압축 실행은 네 개 원문 판정에 실패했습니다. 답변 훅이 `lock-busy`(116ms)를 남기고 원문은 시작/질문/끝이었습니다. [이슈 #101](https://github.com/kodonghui/corthex/issues/101)에 실행·원문·실패/시간 로그를 보존합니다. TC-031은 잠금 경합 때 기록 없이 lock-busy 진단과 exit 0을 허용하므로 이것만으로 TC-066 경계 위반이나 잠금을 잡은 주체를 확정하지 않습니다. 별도 진단 실행은 Windows 자동 시작 경로 일곱 개를 통과했습니다. 제품 수정·모든 정상 턴 기록 보장·앞선 실패의 대체 근거로 보지 않습니다. 옛 질문 누락 관찰 [#98](https://github.com/kodonghui/corthex/issues/98)도 별개로 둡니다.

앞선 독립 검토는 꼭 고칠 것 두 개와 정리 개선 한 개를 고치게 했습니다. 재신뢰 스냅샷은 모든 진단 JSONL을 포함하고, 늦은 끝 기록은 최대 6초 기다린 뒤 같은 판정을 하며, 터미널 실패 정리는 자기 프로세스 그룹을 종료/회수하고 근거 쓰기나 초기 크기 설정이 실패해도 FD를 닫습니다. 제어한 회귀시험은 먼저 실패한 뒤 수정하여 통과하며 끝 누락과 경계 본문도 거부합니다. 실제 Unix 자식/FD 초기화 실패 시험은 Windows에서 환경상 건너뜁니다. 앞선 중단 전체 시험은 미완료로 보존합니다. 그 뒤 Python 3.8 전체 실행은 412개(401 통과·10 건너뜀·실패 1)에서 실패했습니다. 늦은 끝을 만드는 시험 작성자의 한 번뿐인 atomic replace가 Windows 접근 거부를 받았으며 이 실패 실행을 보존합니다. 시험 작성자는 이제 Windows 오류 5/32/33만 최대 2초 재시도하며, 150ms 지연·6초 캡처 한도·정확한 네 원문 판정은 그대로입니다. 일시 공유 거부 한 번을 주입한 시험은 두 Python에서 수정 전 실패하고 수정 뒤 통과했습니다.

두 번째 head `be1cd31dcc6a9128e3569442edae9f9880236e88`의 자동 실행 `41736854148`은 실패했습니다. 단위시험 여섯 칸은 통과했지만 Windows의 Claude clear 네 원문 판정과 Unix의 옛 0.1.0 첫 신뢰 단계가 실패했습니다. 실패 아티팩트 세 개를 받아 API의 SHA256과 일치함을 확인했습니다. 숨김 기억 폴더는 업로드에서 빠져 있었으므로 시작 방식 제어기는 실패 때도 가짜 저장소의 가린 원문 JSONL과 안전한 진단 JSONL만 보이는 `store-evidence` 폴더에 복사하며 계정 파일은 복사하지 않습니다.

제품을 바꾸지 않은 로컬 Windows clear 재현에서는 질문이 빠지고 `lock-busy`가 남았습니다. 두 번째 관측 재현은 질문의 대기 실패 전후에 같은 PID가 프로젝트의 curation/layer 잠금과 해당 원문 잠금을 잡고 있음을 확인했습니다. 그 재현의 유지보수 경합을 확인한 것이며 옛 #98·#101의 원인을 확정한 것은 아닙니다. 시작 방식 제어기는 다음 제어 턴을 보내기 전에 최대 6초 안에서 저장소 잠금이 없는 250ms 구간을 읽기로 확인하고, 관측한 잠금과 대기를 영수증에 남깁니다. 경합 없는 시작 방식 검사의 명시적 사전 조건이며 worker 완료·제품 수정·누락 턴 재시도·무손실 기록 보장이 아닙니다. 같은 네 원문 판정은 기록이 하나라도 빠지면 계속 실패합니다. 수정한 로컬 Windows 실행은 Claude 다섯 경로와 Codex 자동 경로 두 개를 통과했으며 Codex 터미널 경로는 별도 조작 근거를 유지합니다. 제품 잠금 제한과 원래 보관 스트레스 시험은 그대로입니다.

실제 Linux 0.164.0 터미널에서 첫 신뢰 실패를 재현했습니다. 시작 메뉴의 방향키 선택은 신뢰 대신 검토 패널을 열었고, ANSI 화면 갱신이 관측할 글 사이에 끼었습니다. 제어기는 이제 실제 검토를 열고 화면 제어 문자를 뺀 뒤 패널이 안내하는 동작을 확인해 `t`로 신뢰하며 실제 저장된 해시 한 개/네 개 조건은 유지합니다. 수정 Linux 실행은 옛 버전·업데이트 뒤 두 신뢰 단계, 재신뢰 전 원문·진단 불변, 신뢰 뒤 같은 턴의 네 원문과 캐시 45개 파일을 통과했습니다. 메뉴와 ANSI 회귀시험은 고치기 전 실패하고 뒤에 통과했으며 macOS는 최종 CI에서 확인합니다.

독립 검토는 첫 대기 조건이 clear/compact에만 있고 headless 시작/재개/포크에는 빠져 있음을 찾았습니다. 보존한 부하 상태의 Python 3.13 시작도 실패했지만 그 진단만으로 잠금 보유자를 특정하지 않습니다. 시작 방식 전용 복사본은 이제 SessionStart·UserPromptSubmit 관측기를 명시합니다. 관측기가 실제 세션의 원래 시작 훅 자식 종료를 기록하고, 질문 관측기가 잠금 안정 구간을 확인한 뒤 입력·환경·출력·종료 상태를 그대로 유지해 원래 질문 훅 자식을 실행합니다. 원래 후보 해시, 바꾼 훅 설정과 추가 QA 도우미는 따로 기록합니다. 호스트 동작마다 새 세대와 기대 시작 원인을 지정해 재개한 세션이 이전 시작의 완료 영수증을 재사용하지 못하게 합니다. 모든 질문 영수증은 자기 자식 실행 전에 같은 세대 시작 자식의 실제 종료가 있었는지 검사합니다. 원문 누락은 계속 실패하며 이는 시작 방식 검사를 위한 입력 간격 제어이지 원래 훅 전체 시간 측정이나 경합 수정이 아닙니다. 별도의 원래 자식 시간·worker 수명 검사와 업데이트/재신뢰 패키지는 그대로입니다. 두 로컬 Python의 회귀시험은 자식의 바이트·환경·종료 상태 전달을 확인하고 옛 완료 영수증과 잘못된 순서를 거부합니다.

한계: 옛 `<teammate-message`는 유지하며 API fixture로 검사하지만 현재 기본 설정의 실제 입력으로 관찰했다고 보지 않습니다. 두 소유 세션만 쓴 시제품은 이전 제품에서 `<cross-session-message`를 관찰했으나 현재 제품의 세 OS 제어기는 후속입니다. 접두사 판은 `host-prompts-2`이며 일반 판/필드/Stop/Windows 비ASCII와 대화 파일 읽기 방지는 따로 검사합니다. 고정한 Codex 판의 대화 파일 경로는 null입니다. 호스트 프록시 시도는 차단/보존하며 제품 통신 0건으로 바꾸지 않습니다. 한 세션 시간은 p95가 아닙니다. Windows/macOS p95 미달은 미해결입니다. [#95](https://github.com/kodonghui/corthex/issues/95)는 재개 때 API상 닫힘으로 발견해 미달 기록에 맞게 다시 열었고, #96의 부정문 속 종료 키워드를 중립 문구로 바꿨습니다. #98·#101은 열려 있습니다. 실제 에이전트 걷기, 실제 사용자 한 주 시험, 출시 go/no와 명시적 태그 승인은 뒤의 일입니다.
