# 현재 호스트가 만드는 메시지 분기

[English](2026-11-04-memory-native-messages.md)

[호스트 호환성 보고서](2026-11-04-memory-native-compat.ko.md)의 후속입니다. PR #100은 실행 `41753711241`의 12개 작업과 같은 head의 정식 Code/Security 리뷰를 통과해 `982fb4f10e8712aff89e0d472f9a10943283aa68`로 병합됐습니다. 세 산출물의 API 해시를 확인했고, 보이는 임시 저장소 근거가 들어 있습니다. 아래 실제 도구·수명주기·재신뢰·입력 사례는 그 근거를 보존하며, 이번에는 현재 기본 프로필의 부모 에이전트 메시지와 명시적으로 설정한 세션 간 분기를 반복 검사에 더합니다. 원래 제품 파일 45개의 해시는 그 main과 같습니다.

실제 설치한 Claude Code 2.1.310으로 각 운영체제의 세 모드를 실행했습니다. 답변은 고정된 루프백 서버가 제공하며 키와 프로필·프로젝트·저장소는 임시 시험용입니다.

최종 영수증 9개, 실행한 검사기 7개의 해시와 패키지 바인딩은 `native-messages-qualified-v3.json`에 있으며 SHA256은 `23e395d42e6a2a130f5b7876808b036d1a9fcf79d8a868bcae811bde6cbee4e5`입니다. 각 영수증의 검사기 해시는 게시 후보와 같습니다. 실제 설치본 46개 파일은 손대지 않은 제품 파일 44개, 선언한 QA 훅 설정, 원래 측정 helper입니다. 각 영수증은 원래 후보 45개의 해시도 따로 보존합니다. 설정과 helper는 계측이므로 설치본의 전체 훅 설정이 원본 그대로라는 뜻은 아닙니다. Windows와 Unix 설정 해시는 선언한 줄바꿈 차이로 다릅니다.

`native_prefix.py --kind agent`는 실제 백그라운드 에이전트 실행 성공, 일치하는 완료 작업 ID, `main`을 대상으로 한 실제 `SendMessage` 성공과 같은 에이전트가 부모 세션에 보낸 `<agent-message from="…">` 한 개를 요구합니다. 에이전트 메시지와 작업 완료는 모두 UserPromptSubmit에 도달해 `left-out`이 되며, 부모는 서로 맞는 한국어 기록 네 개를 남깁니다. 작업 전용 모드는 따로 유지해 작업 알림 한 개를 확인합니다. 표식과 예약된 메시지 본문은 기억 저장소 어디에도 없습니다. 관찰·미관찰 접두어는 모델 요청 이력이 아닌 실제 훅 입력에서 판정합니다.

`cross_session.py`는 새 호스트 설정 안에 서로 다른 이름의 임시 세션 두 개를 만듭니다. 양쪽은 `crossSessionInbound: accept`, `isolatePeerMachines: true`를 명시합니다. 실제 발신 도구 요청은 살아 있는 소유 수신 세션을 대상으로 해야 합니다. 성공 응답, 실제 `<cross-session-message` 입력의 발신 이름과 수신 세션 ID도 맞아야 합니다. 발신 기록은 네 개, 수신 기록은 정상 턴과 별도 최종 답변·본문 없는 경계를 합쳐 다섯 개입니다. 수신 prompt는 `left-out`, 추가 답변은 다른 turn이며 표식·접두어가 남은 기억 파일은 0개입니다. 다른 사용자의 세션에 보내지 않았으며 기본 수신 정책의 검사는 아닙니다.

통제한 회귀 검사는 다른 부모·에이전트, 관계없는 발신·수신 세션, 중복 전달, 누락되거나 실패한 실제 도구 응답과 설치된 worker 변조를 거부합니다. 이는 판정기 시험이지 호스트 실행 근거가 아닙니다. 패키지 복사 시험은 원래 훅·worker 바이트를 보존하고 관찰기 해시를 선언합니다. 보이는 내보내기는 실패를 포함한 임시 raw와 안전 진단 JSONL만 담습니다. 모델과 소유 프로세스를 닫고 runner 전역도 복원합니다.

첫 Linux 에이전트 영수증에는 실제 검사가 통과했어도 미관찰 접두어 정보가 모순되던 오류가 있었으며 원본을 보존했습니다. 실제 입력 기준 보고로 이를 고쳤습니다. 이전 탐색·LF 정규화 전 영수증도 관찰로 남기되, 게시 검사기 바이트에 묶인 근거는 위의 최종 아홉 개뿐입니다. 제품 런타임·잠금 한도·원래 보관 stress 시험은 바꾸지 않았습니다.

`fd32c2239839`의 정식 코드 리뷰에서 분리된 SessionEnd가 호스트 종료 뒤 끝날 수 있음을 확인했습니다. 이제 실행한 각 임시 세션은 실제 발신·수신 ID로 원래 훅의 마지막 진단까지 최대 6초 기다린 뒤 내보내고 엄격히 판정합니다. 훅을 다시 실행하거나 빠진 줄을 만들지 않으며, 미완성 저장소는 계속 실패하고 부분 근거를 내보냅니다. 기존 즉시 내보내기·읽기 순서는 두 Python 3.8/3.15에서 판정기 여섯 개 중 두 개가 실패하고 수정본은 모두 통과합니다. 통제한 writer는 150ms 뒤 End를, 그보다 늦게 진단을 쓰며 파일 교체에만 기존 Windows 공유 거부의 제한된 재시도를 적용합니다. 첫 red 대조의 메타데이터 오류도 별도로 보존합니다. 이전 v1 집계(`d08fd59659a4aea766960f18cf82fcb9784383508926bb681f3a5e41269e8516`)와 이전 880개 소스 시험은 과거 결과이며, 현재 완료 관찰기에는 v3 영수증 아홉 개만 바인딩됩니다. 이전 Python 3.8 전체 시도는 리뷰 뒤 중단해 미완료입니다. 이는 통제한 지연 근거이며 실제 호스트에서 늦은 End 실패를 관찰했다고 주장하지 않습니다.

보존한 PR #100 근거는 실제 도구·transcript 제외(TC-043), 두 호스트의 시작 원인 다섯 개(TC-066), 입력 필드·버전·비ASCII 및 새 메시지 분기(TC-106), 과거 Codex 0.1.0→0.2.0 신뢰·업데이트·재신뢰(TC-107)를 제공합니다. Windows Codex clear/compact/fork와 재신뢰는 같은 제품 45개에 맞는 별도 해시의 직접 조작 근거이며 Unix는 실제 터미널 CI입니다. Claude transcript에는 도구 표식이 있지만 고정한 Codex의 transcript 경로는 null입니다. API 접근 가드도 transcript를 읽지 않음을 확인합니다. 과거 `<teammate-message`는 API 호환 fixture이며 현재 기본 프로필에서 관찰했다고 주장하지 않습니다.

보존한 CI 측정은 raw 1,000개에서 준비 한 번을 뺀 뒤 훅·호스트마다 100회입니다. 목표 충족은 Linux 8/8, Windows 0/8(p95 114.668–150.640ms), macOS 3/8(73.859–132.079ms)입니다. 유효한 측정이어도 목표 미달을 통과로 올리지 않습니다.

공식 판정은 한영 QA/WBS 행에 적습니다. TC-040은 이미 세었으므로 다시 더하지 않습니다. TC-105의 p95 100ms 목표는 미달이며 [#95](https://github.com/kodonghui/corthex/issues/95), [#98](https://github.com/kodonghui/corthex/issues/98), [#101](https://github.com/kodonghui/corthex/issues/101)은 열린 상태를 유지합니다. TASK-028의 조건은 전체 훅의 시간 보고이며 p95 목표 통과는 아닙니다. 고정 응답 호스트 검사는 TASK-057의 실제 모델 에이전트 걷기, 동의한 실제 사용자 한 주 시범·출시 판단·명시적 태그 승인과 구분합니다. 이번에는 원래 계정 프로필·실제 사용자 활성화·전역 설치·유료 모델 호출을 쓰지 않았습니다.
