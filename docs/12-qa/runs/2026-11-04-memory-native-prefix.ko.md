# Windows에서 실제 작업 알림 확인

[English](2026-11-04-memory-native-prefix.md)

임시 Windows 프로필에서 Claude Code 2.1.310이 실제 백그라운드 에이전트의 작업 완료 알림을 만들었습니다. 실제 `UserPromptSubmit` 훅 입력은 `<task-notification>`으로 시작했습니다. MEMORY는 이를 `left-out`으로 처리했고, 원문에는 원래 시작·사용자 질문·최종 답변(`kind: answer`)·종료 네 개만 남았습니다. 저장소의 어떤 파일에도 알림 접두어나 도구 전용 표식이 없습니다.

고정 답변을 주는 로컬 프로토콜 서버를 쓴 QA 시험이며 실제 모델의 에이전트 걷기나 전체 TC-106 판정은 아닙니다. 제어기가 실제 `Agent` 도구를 요청한 뒤 성공한 실행 결과를 확인하고, 해당 작업 ID와 완료된 훅 알림의 작업 ID가 같은지 확인했습니다. 훅의 세션 ID도 실제 CLI 세션과 같았습니다. 원래 제품 worker는 그대로입니다. 시험용 프로필·동의·대화, 가짜 키와 로컬 모형 주소만 썼으며 실제 제공자 과금·전역 설치·사용자 저장소 활성화는 없습니다.

QA 소스는 `24cc42c5bbb8fe181160528b578ec3d4ebf2e7b8`이고, 제품은 main `2fc4b871873659249e4c43c8b6139c7f5748e186` 그대로입니다. 실제 세션은 2.8초에 끝났고 질문 훅 결과에는 `ok`와 `left-out`이 나왔습니다. 한 번의 관찰이며 성능 백분위의 근거가 아닙니다.

적격 정본은 `task028-prefix-v1/qualified.json`, SHA256 `205eb04537d06f3578e1463cb5c337d4de9a76374597329889d63515a7f42618`입니다. 원래 시험 결과는 미판정 상태로 그대로 보존했습니다. 모델 메시지의 첫 글만 보는 수집기에는 접두어가 잡히지 않았지만 실제 훅 입력에는 있었습니다. 후속 판정은 실제 도구 실행과 그 작업의 완료 입력을 직접 읽었습니다. 첫 판정기는 원문의 종류를 `final`로 잘못 예상했으나 실제 스키마는 `answer`입니다. 이 제어기 오류를 남기고 실제 세션을 다시 돌리지 않은 채 바로잡았습니다.

다른 세션·팀 알림 접두어, Codex의 알림 동작, Linux/macOS의 접두어 실행을 이 결과에서 추정하지 않습니다. CLI가 보여 준 비용은 고정 서버의 시험용 사용량 값으로 계산한 추정치이며 실제 제공자 지출이 아닙니다. 이 관찰만으로 작업·사례·진행률·출시 상태를 올리지 않습니다.
