# NEXUS snapshot CI

After a commit reaches the default branch, `NEXUS push` runs the immutable compatible hub's `push --job --json`. It runs only on default-branch pushes and does not deploy the application.

Use the installed hub's `hub.py setup-ci PROJECT` after setting these values in the session environment:

- `CORTHEX_NEXUS_URL`: the existing non-loopback HTTPS NEXUS origin.
- `CORTHEX_NEXUS_CLIENT_ID`: the Cloudflare Access service client ID.
- `CORTHEX_NEXUS_CLIENT_SECRET`: the matching service secret.

The explicit command configures encrypted repository Actions secrets through `gh secret set` stdin. It never prints the values, puts them in arguments or stores them locally. It resolves the repository from the project's GitHub origin; the project ID `marong` can map to repository `marong2`. If `gh` is missing or not logged in, it skips setup with one line. GitHub permission or transport failures are reported without raw CLI output.

An existing default-branch workflow stays unchanged. A missing workflow gets one reusable PR with immutable action/hub pins, read-only permissions, full project history and serial execution. The command does not merge it or change the local worktree. `setup-ci PROJECT --dry-run` previews without setting secrets or creating a PR. A successful `push PROJECT --first` performs this setup automatically after its upload; it still requires first-upload consent, and a setup failure does not repeat or undo that upload. If the effective upload address differs from the environment's `CORTHEX_NEXUS_URL`, automatic setup skips before any secret write and names the mismatch without printing either address. Ordinary pushes, dry runs and CI jobs do not configure secrets.

## Verify a new CI delivery

1. Read the current `default_commit` and `revision` with an authenticated `GET /api/snapshots/{project}/held`.
2. Merge the next PR and let its `NEXUS push` job publish the new commit before sending it from a local session. In the **Push the snapshot** step, check `answer.sent: true` and confirm that `answer.pushed.default_commit` matches the run's commit.
3. Read the held snapshot again. Confirm the commit and revision match the job's receipt and that the revision increased.

A green run with `why: already-held` confirms the CI can reach the held snapshot and skip a duplicate. Use the next new commit to verify delivery. `not-set` names missing CI settings, and `first-push-waits` means the project needs its approved first upload.

CI never replaces divergent history, passes a checkpoint or deletes project data. The immutable job hub remains compatible with the product's `hub-ref.json`; updating it requires a compatibility check.

Disable `NEXUS push` in Actions to stop automation, or revert its workflow PR. Existing server data remains. Secret rotation or deletion is a separate explicit action; no token is requested or generated by setup.
