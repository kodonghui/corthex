# Stage 12 · QA

| Slot | This stage |
| --- | --- |
| Inputs | User flows (FL), the acceptance criteria in the functional spec (SPEC), the responses and error codes in the API contract (API), the screen states (SCR) and the non-functional requirements (REQ) |
| Outputs | `test-plan.md`, by default `docs/12-qa/test-plan.md`, with TC IDs mapped to FL, SPEC, API responses, screen states and non-functional REQ, and the way each case runs; automated tests, such as contract tests and end-to-end tests with Playwright; bug reports with BUG IDs |
| Human view | By default the test plan and the test report in the repository, with bugs as issues in the tracker, as set in `human` |
| Sync | Test runs update the plan. Each bug links the test case, the screen, the spec row and the API response it breaks |
| Human checkpoints | The release decision: go or no-go |
| Trace IDs | TC-001…, BUG-001…; a case names the responses and states it checks, such as `API-001#401` and `SCR-002#permission` |

## Steps

1. Write test cases from the flows and the acceptance criteria, not from the code.
2. Add a case for each response in the API contract, such as `API-001#401`, and for each screen state, such as `SCR-002#permission`. One case can cover several of them, and the contract tests (stage 11) cover many responses at once. A response a real server cannot be made to return on purpose, such as `default`, is checked on the screen against the mock server (stage 06).
3. Write each expected result as the response and its effects: the status, the error code from the contract's list, and what changed in the data or that nothing did, such as no order saved, counts unchanged or no AI call made. Contract tests check only the response, so check the data separately.
4. For a behaviour that calls an AI model, add cases with questions inside its scope and outside it, such as an unrelated request or one that asks it to ignore its rules. Expect what its AI call entry (stage 04) says: the output format, the server's checks, and that the data marked as not sent never reaches the model. Most cases can run against recorded answers; mark the ones that call the real model, since they cost money and their answers vary.
5. Say how each case runs: `contract` for the contract tests, `e2e` for end-to-end tests that drive the screens, for example with Playwright, or `manual`. Automate the cases that run often or guard money, data or access.
6. Run the plan on a development or staging server, never on production. Create the test accounts with a seed script and keep their passwords in the secret store; cases and reports name only their roles, such as anonymous, signed-in user, another user and administrator.
7. Measure each performance requirement as it is written, with its percentile, load and environment. Report measurements on a developer's machine apart from the deployed environment, and back a claim that a change made something faster with runs before and after it under the same conditions.
8. Record each result with where it ran and the commit, such as `pass on staging (commit abc1234)`. A pass against the mock server shows that the screen handles the response, not that the server returns it. File bugs with the trace ID of the failing response.
9. Report coverage as counts: how many flows, acceptance criteria, responses and screen states have a passing case, out of how many, and what was not run.

## Checks

- Every flow's main path and main failure paths have a test case.
- Every acceptance criterion has a test case.
- Every response in the API contract and every applicable screen state has a test case.
- Every expected result names the status, the error code where there is one, and the effect on the data.
- Every non-functional Must requirement (REQ) has a test case or a stated way to check it.
- Every behaviour that calls an AI model has cases inside and outside its scope.
- Every performance result names its percentile, its load and where it ran.
- Every result says where it ran and against which commit.
- Every bug has steps, expected and actual results, the environment, the trace ID of a failing response and evidence.
- The report gives the counts and names what was not run.
