# Stage 12 · QA

| Slot | This stage |
| --- | --- |
| Inputs | User flows (FL), the acceptance criteria in the functional spec (SPEC), the responses and error codes in the API contract (API), the screen states (SCR) and the non-functional requirements (REQ) |
| Outputs | By default `docs/12-qa/` holds `test-plan.md`, with TC IDs mapped to FL, SPEC, API responses, SCR and non-functional REQ; `bugs/`, with one Markdown file per BUG; `runs/`, with walk reports, release gate reports and after-release records; and `verify/`, with the verification runbook. Keep contract tests, API tests that fire every listed response (by default in `tests/api/`) and pinned end-to-end tests in the repository |
| Human view | On a project on NEXUS, by default NEXUS's list of the cases and bugs; otherwise the test plan, test and run reports and bug files in the repository, as set in `human` |
| Sync | Test runs update the plan. Each bug links the test case, screen, spec row and API response it breaks. The agent reads the plan and bug files to apply the release gate |
| Human checkpoints | The go/no-go release decision after the release gate, with its known risks and recorded waivers. The user answers it, whatever `checkpoints` says |
| Trace IDs | TC-001…, BUG-001…; a case names the responses and states it checks, such as `API-001#401` and `SCR-002#permission` |

## Steps

1. Write test cases from the flows and the acceptance criteria. Each arrow in a stage 03 user flow is a transition. Name it by the flow and the two steps it connects. Cover every transition at least once in the run list and add failure transitions for risky states. Cover role, device, permission state, network and sign-in state in a pairwise table instead of turning each combination into a new path. Use three-way combinations only for gate areas.
2. Add a case for each response in the API contract, such as `API-001#401`, and for each screen state, such as `SCR-002#permission`. One case can cover several of them, and the contract tests (stage 11) cover many responses at once. Use controlled fault injection on disposable development/staging targets to trigger framework and internal errors, including 500s. If a response cannot safely be triggered, mark the server path untested with its reason; a mock-server screen check (stage 06) covers only the client.
3. Go through the kinds of cases below for each behaviour and add the cases that apply. Mark a kind that cannot happen as not applicable, with the reason.
4. Write each expected result as the response and its effects: the status, the error code from the contract's list, and what changed in the data or that nothing did, such as no order saved, counts unchanged or no AI call made. Contract tests check only the response, so check the data separately.
5. For a behaviour that calls an AI model, add the cases of [ai-cases.md](ai-cases.md), with its red-team cases where the model talks with people or holds tools.
6. Say how each case runs in `Runs as`: `contract` for contract tests, `api` for an API test that sends the request itself, `e2e` for an end-to-end test that drives the screens, `agent` for an agent walk, `manual` for human execution, or `device` for a real-device check. In the `Gate` column, mark a case `gate` if it covers a release path or an S1-class risk. Include install and update, sign-in and access, payment and money, data migration, deletion and backup, and any case whose failure would be S1 ([bug-fix.md](bug-fix.md)). Automate the cases that run often or guard money, data or access.
7. Run the plan on a development or staging server, never on production. Start the product, check it and clean up by its verification runbook ([verify-runbook.md](verify-runbook.md)); a product without one gets one first. Create the test accounts with a seed script and keep their passwords in the secret store; cases and reports name only their roles, such as anonymous, signed-in user, another user and administrator.
8. Fire every response. For each operation, send the request that should get each response it lists, the way Try it out sends it in Swagger UI, and check the status, the error code, the error shape and the effect on the data. Count responses checked only against the mock server separately; they do not prove the back end returns them (step 2). Keep these requests as API tests in the repository, by default in `tests/api/`, so they run again after every change; the contract tests add generated requests on top of them.
9. Walk every kind of screen people use on every QA run, without waiting for the user to ask. This comes on top of the project's own tests. Walk the flows the changes touch, and every flow before a release, after a large change and when the user asks. Use development or staging, walk as each role that uses the flows, and report the tool, verdicts, evidence and impressions. Use Aside, then ego lite, then Playwright where the preceding tools cannot be reached, and agent-desktop for desktop windows ([browser-agents.md](browser-agents.md)). Use [device-agents.md](device-agents.md) for mobile apps. Walk even a single screen. A product with no screens records why the walk was skipped.
10. Pin what works. Turn successful coverage rows into end-to-end tests and run them on every pull request. Treat an agent's verdict as a claim. A row passes on screenshots and the data check, or on a pinned test's assertions. A test agent such as Playwright's healer may fix locators and waits in a pinned test. Keep the assertions and expected results as written. A skip it adds counts as not passed.
11. Before a bulk or performance run, verify the actual target, environment, deployed revision and effective AI mode without a paid model probe. Ordinary runs require fake mode; stop on real, disabled, unknown or stale state. A real-model run needs its own approved target, data, spending limit and run scope. Then measure each performance requirement as it is written, with its percentile, load and environment. Report measurements on a developer's machine apart from the deployed environment, and back a claim that a change made something faster with runs before and after it under the same conditions.
12. Record each result as described below. A pass against the mock server covers the screen's handling of the response. File bugs with the trace ID of the failing response, and fix each one by [bug-fix.md](bug-fix.md). List testers' impressions apart from bugs. The user decides which become bugs, tasks or changes to the requirements.
13. Report passing cases out of the total for flows, acceptance criteria, API responses and screen states. Count mock-only responses separately and name what was not run. Report the walk as “N of M transitions on commit X with tool Y”, counting distinct transitions with recorded evidence.
14. For a device rollout, name the first group, success signal and deadline in the plan before go/no-go. Apply the release gate before asking. After the authorized release, complete the after-release check.

## Results

Put one of these results in the plan's `Status` column:

| Status | Meaning |
| --- | --- |
| `pass` | The evidence meets the expected result |
| `fail` | The evidence shows the expected result was missed |
| `blocked` | The case could not run or finish. Give the reason |
| `not run` | The case was not run under the required conditions |
| `waived` | The user waived the named case. Cite the recorded decision (DEC) |

Treat any other wording, including “pending”, “partial” or “not met”, as not passed. In `Run evidence` keep the environment, commit and supporting evidence. For an unrun or waived case, name the intended environment and commit and say that no qualifying run took place.

### Migrating a legacy plan

Replace `Last result` with `Status` and `Run evidence`. Keep the original text and its environment, commit and evidence in `Run evidence`. Use the leading verdict when it clearly gives one of the five values. For example, `pass on staging (commit abc1234)` becomes `pass` with its evidence in the separate column. Use `blocked` only with a reason and `waived` only with the user's decision. Map ambiguous or unsupported verdicts to `not run`. Keep any forced evidence marked `forced` and apply the rule below before recording a pass.

Until these rows are migrated, count them separately in the gate report as “needs format migration”. Resolve their results before using them in the gate or asking for go/no-go.

### Forced runs

A case about platform behaviour can pass only under unforced conditions. This applies to background work, scheduled jobs, install and update, notifications, power saving and permissions the system grants. Mark evidence as `forced` if the tester ran a job by hand (such as `adb shell cmd jobscheduler run`), shifted the clock, used a test broadcast in place of the system or otherwise forced the behaviour. Such runs check the logic and count as `not run` for the gate. For each platform case, name the unforced check it needs and mark the real-device check `device`. Keep forced and unforced evidence identifiable when both exist.

## Release gate

Before the go/no-go checkpoint, read the plan, bug records and pinned test results for the release commit. Each of these blocks release:

- Any `fail`.
- Any `gate` case without a `pass`, except a `waived` case with the user's DEC for that named item.
- Any open S1 or S2 bug. A `fixed` S1 or S2 production-incident bug with steps still owed also blocks, except for further fixes for that incident ([bug-fix.md](bug-fix.md#production-incidents)).
- Any pinned end-to-end test of a `gate` case that is skipped or marked `fixme`.

When a gate case cannot pass before release because it needs real users' devices or days of time, ask for a go for the first group only. Other blockers still apply to that group. The wider release waits for the case to pass. If it fails or the signal times out, keep the wider release on hold and open a bug.

For any other exception, the user must answer for the named blocking item and the answer goes in a DEC, as in step 4 of the `corthex` skill's change procedure. An agent never waives a case. A bulk go does not clear a blocking item.

List the other cases without a `pass` as known risks in the release report, with each result, reason and follow-up. Show the list at the checkpoint. The user's go accepts that list as a whole. Report counts for blocking items, known risks and waivers, with the decisions for the waivers.

## After release

- **Web.** After each production release, browser agents walk the flows that change nothing on production, on the released commit. Record the verdicts and evidence.
- **Releases to users' devices.** Release to a first group (canary), such as one device. Use the store's staged rollout for a store app. Check for the signal and deadline named in the plan, such as the app reporting the installed version to the server by a stated time. Widen only after the signal arrives and the gate permits widening. If it does not arrive in time, open a bug and record the rollout as held.
- Record the released commit and the outcome for each production release. For a canary, include the first group, the signal, the time it took (or the elapsed time at timeout) and when the release widened or why it is held.

## Kinds of cases

Stages 04, 06 and 08 use the same kinds, so that every case the spec names has a response, a screen state and a test.

| Kind | Cases | Expected, for example | Runs as |
| --- | --- | --- | --- |
| Access | Signed out; an expired sign-in; another user's item; a user calling an administrator's operation; an administrator | 401; 401 and sign in again; 403, or 404 where the contract hides the item; 403; success. A refused request changes nothing | `contract`, `api`, `agent` |
| Input | An empty required value; a value too long; the wrong format; a number out of range; a dangerous value, such as a URL with a script scheme or a negative position; each sent straight to the API as well as through the screen | 400 or 422 with its error code, and nothing saved. The server's limits equal the columns' (stage 05) | `contract`, `api` |
| Target | An ID that does not exist; an ID in the wrong format; an item already deleted | 404; 400; 404 or the code the contract decides. Never 500, and nothing changes | `contract`, `api` |
| State changes | A change the state does not allow; going back a step; reopening a closed item; changing to the state it already has | 409 with its error code. The same state again does what stage 04 decides, such as success with nothing changed | `api` |
| Repeats | Sending again after a lost response; a double click; the same update twice | One result, and the second request gets the same answer | `api`, `agent` |
| Concurrency | Two users changing one item at once; two users claiming one resource at once | 409, or one change applied. Nothing is broken or duplicated | `api` |
| Limits | Too many requests; the free uses of an AI feature used up; a cost limit reached | 429 or the code the contract decides. A refused request makes no AI call and uses no tokens, and the screen says why | `api`, `agent` |
| Outside services | A service with controlled delay, phase timeout, exhausted total deadline including SDK retry/backoff, provider failure or no key; cancellation and disconnects | The fallback the spec decides, or 502, 503 or 504. The rest keeps working | `api`, `agent` |
| Data exposure | Personal data, internal error details, and fields the screen hides but the response carries | None of them in the response body | `api`, `manual` |
| Empty and streamed answers | 204 with no body; an empty list; a stream cut off midway; a closed connection | The screen shows its empty state or a retry, and does not hang | `api`, `e2e` |
| Screen states | Loading, empty, error, permission and stale; back to sign-in after a 401; a narrow screen and long text | What the screen definition (stage 08) says, and every action still usable | `agent`, `e2e` |
| AI answers | A question in scope; a question out of scope; a forbidden request, such as one asking for a guarantee; messages sent at their real intervals while it answers; a photo with text; voice; a way in that skips the AI | The format of the AI call entry (stage 04). A forbidden request gets its fixed answer without a model call. Messages that arrive while it answers get what stage 04 decides, and each write runs once | `api`, `manual` |

## Checks

- Every transition has a test case in the run list, including failure transitions for risky states. The pairwise table covers environment factors, with three-way combinations only in gate areas.
- Every acceptance criterion has a test case.
- Every response in the API contract and every applicable screen state has a test case.
- Every kind of case has cases for each behaviour it applies to, or is marked not applicable with the reason.
- Every expected result names the status, the error code where there is one, and the effect on the data.
- Every response the contract lists is fired by an API test in the repository, against a development or staging server, or the report names the untested server path and why. A response which is checked against the mock server is counted apart and never qualifies that server path.
- Every QA run, on top of the project's own tests, walks the changed flows on every kind of screen the product has, including a product with one screen. The report names the browser, desktop or device tool, and gives the reason if the product has no screens.
- Before a release, agents walk every flow on the release commit for each role that uses it. Record any coverage that could not run and why.
- Every coverage verdict cites screenshots and the data check or a pinned test's assertions, and impressions are reported apart from bugs.
- Every non-functional Must requirement (REQ) has a test case or a stated way to check it.
- Every behaviour that calls an AI model has cases inside and outside its scope.
- Every evaluation of the real model says how many times each case ran and the uncertainty, and compares before and after on the same cases.
- A product whose AI talks with people or holds tools has red-team cases for each category that applies, run three times on the current prompt, knowledge and model, and names the categories left out with the reason.
- Every performance result names its percentile, its load and where it ran.
- Every case uses one of the five `Status` values and records its environment and commit. Every platform-behaviour case names its unforced or real-device check and labels forced evidence.
- The release gate report counts blocking items, known risks and waivers with their decisions. Every release has an after-release record.
- Every bug has a status, severity, priority, where it was found, defect type, cause stage, steps, expected and actual results, environment, trace ID and evidence. Every bug found after release has an escape analysis.
- Every fixed bug names the stage of its cause and a regression test case that failed before the fix and passes after it, or the corrected case or gate and its evidence for a Test or gate defect, as [bug-fix.md](bug-fix.md) says.
- The report gives the counts and names what was not run.

## Output template

Write the plan as `docs/12-qa/test-plan.md` by default. The hub reads the `Status` column. `Gate`, `Runs as` and `Run evidence` stay in the plan for the agent to read.

```markdown
| ID | Case | From | Runs as | Gate | Steps | Expected | Status | Run evidence |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| TC-001 | Order with a failing payment | FL-001, SPEC-001, API-001#422 | api, agent | gate | As a signed-in user, pay with a declined card | 422 `payment_failed` and its message by the card; the order is cancelled and nothing is charged | pass | Staging, commit abc1234. See run R01 for the screenshot and data check |
| TC-002 | Open another account's order | FL-002, API-002#403, SCR-002#permission | contract, agent, e2e | gate | As another user, open the order | 403 `forbidden`; "This order belongs to another account" and a link home; the order is unchanged | not run | Planned for staging on commit abc1234. No qualifying run |

Coverage at commit abc1234: passing cases cover 1 of 2 flows, 1 of 1 acceptance criteria, 1 of 9 API responses and 0 of 3 screen states. The walk covered 1 of 2 transitions on commit abc1234 with Aside. Not run: TC-002.

Release gate: 1 blocking item (TC-002), 0 known risks, 0 waivers.
```

Write each bug in its own file, such as `docs/12-qa/bugs/BUG-001.md`. The hub reads the ID, title, status and priority from the front matter and the trace IDs from the body. Keep `severity`, `found_in`, `defect_type` and `cause_stage` in the file for QA. Without a stage override, the hub reads `test-plan.md` and the Markdown bug files in `docs/12-qa/bugs/`. Existing projects can keep an explicit `source` of `docs/12-qa/test-plan.md` and their in-plan BUG entries. Explicit sources continue to follow the project's settings.

```markdown
---
id: BUG-001
title: Cancel button stays enabled after payment
status: fixed
severity: S2
priority: P1
found_in: production
defect_type: Spec
cause_stage: "08"
---

From: TC-004 · SCR-002 · SPEC-005
Cause: The screen definition has no state for a paid order. The fix adds it.
Steps: Pay for an order and reopen its details.
Expected: A paid order has no cancel action.
Actual: The cancel button stays enabled.
Environment: Production web on commit abc1234.
Found on: 2026-10-24.
Trace ID: API-001#200
Evidence: Redacted screenshot of the paid order and its available actions.
Escape: TC-004 checked the payment response alone. The gate accepted a pass without checking the paid screen state. Add the paid-state check to TC-004.
Regression test: TC-004 failed on commit abc1234 and passes on commit def5678.
```

Keep run reports under `docs/12-qa/runs/`. Name reports after the run. The default hub scan leaves out run reports and their evidence. When writing a report, mention trace IDs in sentences or use a run row ID as the first column of a table, with trace IDs inside descriptive text. Reserve headings led by a trace ID, columns of bare trace IDs and item front matter for source definitions and trace tables. See the [run report template](browser-agents.md#the-report).
