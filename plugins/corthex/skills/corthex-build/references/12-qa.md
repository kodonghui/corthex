# Stage 12 · QA

| Slot | This stage |
| --- | --- |
| Inputs | User flows (FL), the acceptance criteria in the functional spec (SPEC), the responses and error codes in the API contract (API), the screen states (SCR) and the non-functional requirements (REQ) |
| Outputs | `test-plan.md`, by default `docs/12-qa/test-plan.md`, with TC IDs mapped to FL, SPEC, API responses, screen states and non-functional REQ, and the way each case runs; automated tests: contract tests, API tests that fire every listed response, by default in `tests/api/`, and end-to-end tests, such as with Playwright; a report of each browser agent run, by default in `docs/12-qa/runs/`, with what works, what does not and the testers' impressions; bug reports with BUG IDs |
| Human view | By default the test plan, the test report and the run reports in the repository, with bugs as issues in the tracker, as set in `human` |
| Sync | Test runs update the plan. Each bug links the test case, the screen, the spec row and the API response it breaks |
| Human checkpoints | The release decision: go or no-go |
| Trace IDs | TC-001…, BUG-001…; a case names the responses and states it checks, such as `API-001#401` and `SCR-002#permission` |

## Steps

1. Write test cases from the flows and the acceptance criteria, not from the code.
2. Add a case for each response in the API contract, such as `API-001#401`, and for each screen state, such as `SCR-002#permission`. One case can cover several of them, and the contract tests (stage 11) cover many responses at once. Use controlled fault injection on disposable development/staging targets to trigger framework and internal errors, including 500s. If a response cannot safely be triggered, mark the server path untested with its reason; a mock-server screen check (stage 06) covers only the client.
3. Go through the kinds of cases below for each behaviour and add the cases that apply. Mark a kind that cannot happen as not applicable, with the reason.
4. Write each expected result as the response and its effects: the status, the error code from the contract's list, and what changed in the data or that nothing did, such as no order saved, counts unchanged or no AI call made. Contract tests check only the response, so check the data separately.
5. For a behaviour that calls an AI model, add cases with questions inside its scope and outside it, such as an unrelated request or one that asks it to ignore its rules. Expect what its AI call entry (stage 04) says: the output format, the server's checks, and that the data marked as not sent never reaches the model. Use scripted fakes for delay, timeout, refusal, malformed output and provider failures, and verify that unrelated operations remain responsive and refused requests change no data. Fixed answers alone do not exercise these failure paths. Most answer cases can run against recorded answers through the fake client (stage 11); mark the ones that call the real model, since they cost money and their answers vary, and run them only when asked, with a key set. To judge the real model's answers, run each case at least three times and report pass@1 together with pass^k, the share of cases that pass every run. Compare a change with runs before and after it on the same cases and scripts, pair by pair; grade by the state of the data, such as what was saved or submitted, not by the wording; and use the production model settings file with a separate test key and development or staging targets (step 7). Keep a regression set of cases that pass apart from a capability set of cases to improve, and add real failures to them. Check a model grader against a sample graded by people, and report the number of runs and the uncertainty; the product sets the counts, with at least three runs per case. Before running real-model cases, check the test key's balance and limit (stage 11). When the model holds write tools, add cases of impersonation, someone else's evidence and instructions inside an attachment or a tool result. When it talks with people or holds tools, also run the red-team cases below.
6. Say how each case runs: `contract` for the contract tests, `api` for an API test that sends the request itself, `e2e` for an end-to-end test that drives the screens, such as with Playwright, `agent` for browser agents walking a flow, or `manual`. Automate the cases that run often or guard money, data or access.
7. Run the plan on a development or staging server, never on production. Create the test accounts with a seed script and keep their passwords in the secret store; cases and reports name only their roles, such as anonymous, signed-in user, another user and administrator.
8. Fire every response. For each operation, send the request that should get each response it lists, the way Try it out sends it in Swagger UI, and check the status, the error code, the error shape and the effect on the data. Count responses checked only against the mock server separately; they do not prove the back end returns them (step 2). Keep these requests as API tests in the repository, by default in `tests/api/`, so they run again after every change; the contract tests add generated requests on top of them.
9. Walk the flows in a real browser on every QA run, without waiting for the user to ask. This comes on top of the project's own tests: a project that already has unit, API or end-to-end tests, or a QA script of its own, runs them as before. Browser agents then walk the flows that the run's changes touch, and every flow before a release, after a large change and when the user asks, on localhost or a deployed development or staging site, as each role that uses it, and report what works, what does not and their impressions, such as what was hard to use or looked wrong. They drive ego lite, or Aside where ego lite cannot be reached, and Playwright only where neither can, and the report names the tool. Only a product with no screens in a browser skips this step, with the reason. How to run them is in [browser-agents.md](browser-agents.md).
10. Pin what works. Turn the rows the browser agents walked without a failure into end-to-end tests, such as with Playwright, and run those on every pull request; browser agents cannot run in CI.
11. Before a bulk or performance run, verify the actual target, environment, deployed revision and effective AI mode without a paid model probe. Ordinary runs require fake mode; stop on real, disabled, unknown or stale state. A real-model run needs its own approved target, data, spending limit and run scope. Then measure each performance requirement as it is written, with its percentile, load and environment. Report measurements on a developer's machine apart from the deployed environment, and back a claim that a change made something faster with runs before and after it under the same conditions.
12. Record each result with where it ran and the commit, such as `pass on staging (commit abc1234)`. A pass against the mock server shows that the screen handles the response, not that the server returns it. File bugs with the trace ID of the failing response. List the testers' impressions apart from the bugs; the user decides which become bugs, tasks or changes to the requirements.
13. Report coverage as counts: how many flows, acceptance criteria, responses and screen states have a passing case, out of how many, how many responses were checked only against the mock server, how many flows the browser agents walked on which commit and with which tool, and what was not run.

## Red-team cases

For a product whose AI talks with people or holds tools:

1. Choose the categories that apply, and give the reason for each one left out: direct injection, indirect injection, impersonation and identity bypass, fake evidence, social engineering, financial fraud, personal data, unreasonable demands, crisis signals, and runaway or false answers.
2. For each category, write scenarios over several turns, with pressure and attachments.
3. Judge the answer and the tool calls together.
4. Run each scenario three times; one break is a failure.
5. Run them again whenever the prompt, the knowledge or the model changes.
6. For crisis signals, check the contacts and the laws for the country and the date.

## Kinds of cases

Stages 04, 06 and 08 use the same kinds, so that every case the spec names has a response, a screen state and a test.

| Kind | Cases | Expected, for example | Runs as |
| --- | --- | --- | --- |
| Access | Signed out; an expired sign-in; another user's item; a user calling an administrator's operation; an administrator | 401; 401 and sign in again; 403, or 404 where the contract hides the item; 403; success. A refused request changes nothing | `contract`, `api`, `agent` |
| Input | An empty required value; a value too long; the wrong format; a number out of range; a dangerous value, such as a URL with a script scheme or a negative position; each sent straight to the API as well as through the screen | 400 or 422 with its error code, and nothing saved. The server's limits equal the columns' (stage 05) | `contract`, `api` |
| Target | An ID that does not exist; an ID in the wrong format; an item already deleted | 404; 400; 404 or the code the contract decides. Never 500, and nothing changes | `contract`, `api` |
| State changes | A change the state does not allow; going back a step; reopening a closed item; changing to the state it already has | 409 with its error code. The same state again does what stage 04 decides, such as success with nothing changed | `api` |
| Repeats | Sending again after a lost response; a double click; the same update twice | One result, and the second request gets the same answer | `api`, `agent` |
| Concurrency | Two users changing one item at once; two users claiming one resource at once | 409, or one change applied. Nothing is broken or duplicated | `api` |
| Limits | Too many requests; the free uses of an AI feature used up; a cost limit reached | 429 or the code the contract decides. A refused request makes no AI call and uses no tokens, and the screen says why | `api`, `agent` |
| Outside services | A service with controlled delay, phase timeout, exhausted total deadline including SDK retry/backoff, provider failure or no key; cancellation and disconnects | The fallback the spec decides, or 502, 503 or 504. The rest keeps working | `api`, `agent` |
| Data exposure | Personal data, internal error details, and fields the screen hides but the response carries | None of them in the response body | `api`, `manual` |
| Empty and streamed answers | 204 with no body; an empty list; a stream cut off midway; a closed connection | The screen shows its empty state or a retry, and does not hang | `api`, `e2e` |
| Screen states | Loading, empty, error, permission and stale; back to sign-in after a 401; a narrow screen and long text | What the screen definition (stage 08) says, and every action still usable | `agent`, `e2e` |
| AI answers | A question in scope; a question out of scope; a forbidden request, such as one asking for a guarantee; messages sent at their real intervals while it answers; a photo with text; voice; a way in that skips the AI | The format of the AI call entry (stage 04). A forbidden request gets its fixed answer without a model call. Messages that arrive while it answers get what stage 04 decides, and each write runs once | `api`, `manual` |

## Checks

- Every flow's main path and main failure paths have a test case.
- Every acceptance criterion has a test case.
- Every response in the API contract and every applicable screen state has a test case.
- Every kind of case has cases for each behaviour it applies to, or is marked not applicable with the reason.
- Every expected result names the status, the error code where there is one, and the effect on the data.
- Every response the contract lists is fired by an API test in the repository, against a development or staging server, or the report names the untested server path and why. A response which is checked against the mock server is counted apart and never qualifies that server path.
- Every QA run, on top of the project's own tests, had browser agents walk the flows its changes touch, with ego lite or, where it could not be reached, Aside, and the report names the tool and, when neither could be reached, why.
- Before a release, browser agents have walked every flow on the release's commit, for each role that uses it, or the report names the flows not walked and why.
- Every verdict of a browser agent has its evidence, and impressions are reported apart from bugs.
- Every non-functional Must requirement (REQ) has a test case or a stated way to check it.
- Every behaviour that calls an AI model has cases inside and outside its scope.
- Every evaluation of the real model says how many times each case ran and the uncertainty, and compares before and after on the same cases.
- A product whose AI talks with people or holds tools has red-team cases for each category that applies, run three times on the current prompt, knowledge and model, and names the categories left out with the reason.
- Every performance result names its percentile, its load and where it ran.
- Every result says where it ran and against which commit.
- Every bug has steps, expected and actual results, the environment, the trace ID of a failing response and evidence.
- The report gives the counts and names what was not run.
